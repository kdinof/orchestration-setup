# Сборка бэклога задач для оркестрации

Как получить из сырой идеи/PRD план задач, пригодный для `/orchestrate`: карточки самодостаточны, параллель безопасна, приёмку может проверить reviewer с чистым контекстом. Историческая методика из AI Course Builder; следующие пути — примеры из того проекта, не файлы этого репозитория: `research/research-plan.md` (research-бэклог), `outputs/agent-dev-plan.md` (план разработки), `research/answers/` (26 артефактов-решений).

**Схема целиком:**

```
Идея/PRD
  → (A) research-бэклог: найти и закрыть неизвестные ВОЛНАМИ агентов
  → (B) план разработки: изолированные задачи, волны, gate'ы
  → (C) формат под tasks/_generate.py → раны → /orchestrate
```

Главный принцип: **план разработки пишется только на проверенных решениях.** Каждое «наверное» в плане превращается в возвращённую задачу, сорванную волну или переделку контракта посреди рана. Проверяй блокирующие неизвестные ограниченными спайками; сроки и стоимость зависят от проекта и измеряются, а не гарантируются.

---

## A. Research-фаза: закрыть неизвестные до плана

### A1. Найти неизвестные

Пройди по PRD и выпиши в список:
- каждое **число-обещание** (метрики вида «точность ≥95%», «черновик ≤20 минут») — их достижимость надо ИЗМЕРИТЬ до плана, это будущие спайки;
- каждый **выбор технологии**, который PRD не зафиксировал (парсер, редактор, очередь, ESP, модель);
- каждое «**уточняется при реализации**» — прямой маркер дырки;
- **интеграционные и юридические риски** (доставляемость, персданные, лицензии, доступность API из региона);
- **данные**: на чём будем проверять качество (eval-корпус) — почти всегда самый длинный lead time, зависит от владельца.

Отфильтруй: не ресерчить уже закрытое (существующие отчёты) и то, что дешевле проверить кодом внутри задачи разработки. Из оставшегося выдели **топ-риски** — «из-за чего проект может не сойтись» (обычно 5–8 штук). Их закрывают спайками с числами, не чтением статей.

### A2. Оформить research-план (он же трекер)

Один документ (`research/research-plan.md` как образец). Каждая задача:

- **ID**: буква трека + номер (A1, B3, D5…) — на них будут ссылаться карточки плана разработки;
- **Вопросы** — конкретные, на которые существует ответ;
- **Блокирует** — какой этап будущего плана (или «не блокер»);
- **Метод** — один из четырёх: `[deep-research]` (веб, полностью параллелится), `[spike]` (код/API, нужны материалы и окружение), `[decision]` (короткий анализ + решение владельца), `[user]` (инпут, который может дать только владелец);
- **Артефакт** — файл `research/answers/<ID>-<slug>.md`.

Правила документа:
- **Правило закрытия:** задача закрыта, когда артефакт содержит секцию «## Вывод для V1» с явным решением («берём X, потому что…»), а не обзор вариантов.
- **Секция §0 «Статус»** обновляется после каждой волны — план сам является трекером; сессию можно убить и продолжить по нему.
- **Секция «Вопросы владельцу»** — отдельно; агенты их не решают.
- **Критический путь** — назови явно цепочку «самое длинное/рискованное» и стартуй её первой (в обкатке: корпус → спайк citations → экономика). Остальное параллелится вокруг.

### A3. Исполнение волнами

**Волна 1 — исследование (в пределах лимита активных агентов).** По агенту на 1–2 смежные задачи. В промпт каждому: контекст продукта (3–5 предложений — агент не видит разговора), конкретные вопросы, формат артефакта («## Вывод для V1» → обоснование → сравнение → источники), путь файла, «верни 3–5 предложений с выводом». Данные для будущих спайков собирает отдельный агент уже в этой волне: если реальных материалов нет — суррогатный корпус из публичных документов (приёмка потом всё равно на реальных).

**Волна 2 — спайки (после волны 1, главный риск первым).** Спайк обязан вернуть **числа** (измеренную точность / стоимость / латентность / скорость), а не мнение. Если целевая метрика не достигнута наивным способом — одна итерация улучшенной механики обязательна, и только потом вердикт. Каждому спайку: своя директория `research/spikes/<ID>/`, свой venv, запрет трогать чужое, секреты только из `.env` и никогда в артефакты. Прототипы спайков (редактор, узлы графа) сохраняются — это референс-код для задач разработки.

**Волна 3 — синтез-решения (после спайков).** Агенты читают ТОЛЬКО локальные артефакты (веб не нужен) и закрывают развилки: лимиты, спецификации, итоговый стек, экономика. Это самые дешёвые задачи — не смешивать их с ресерчем: сначала факты, потом решения.

Открытые хвосты («изоляция упавшей ветки не проверена») не прячутся — помечаются в артефакте и потом явно мапятся на конкретную задачу плана («закрывается мини-спайком в T1.9»).

### A4. DoD research-фазы

- [ ] все задачи «Блокирует Этап 0/1» имеют артефакт с «Вывод для V1»;
- [ ] каждое число-обещание PRD подтверждено измерением или скорректировано;
- [ ] стек зафиксирован до уровня библиотек (один сводный артефакт — будущий обязательный контекст всех карточек);
- [ ] хвосты перечислены, и ни один не блокирует старт разработки;
- [ ] вводные владельца собраны в одну секцию с пометкой «что именно блокирует».

## B. План разработки: спроектировать бэклог

### B1. Единица — задача

Задача = работа одного агента за одну сессию. Критерии качества карточки:

| Свойство | Тест |
|---|---|
| Размер S/M/L (≤1ч / 1–3ч / 3–6ч) | больше L → дробить по слоям (ядро отдельно, панель/интеграция отдельно) |
| Одна область владения | список путей, которые МОЖНО менять; всё остальное read-only |
| Контекст-пакет 2–4 файла | ссылки на артефакты `research/answers/` и секции PRD, НЕ пересказ (пересказ расходится с источником при первом обновлении) |
| Проверяемая приёмка | см. B4 |
| Нет «и т.д.», «по аналогии», «при необходимости» | каждое такое место — будущий вопрос сабагента или самодеятельность |

Карточка должна отвечать на четыре вопроса: **что сделать, где можно менять, что прочитать, как поймём что готово.**

### B2. Скелет: этапы → волны

- **Этапы** — из плана реализации PRD, каждый с **gate** (интеграционная проверка; формулируй как исполняемый сценарий, не как «этап завершён»). Gate — это граница рана.
- **Волны** внутри этапа — параллелимые пачки: области владения не пересекаются, зависимости только на предыдущие волны. Внутри волны порядок строк = порядок для одиночного агента (никакой отдельной «последовательной» версии плана не нужно).
- Типовая форма этапа-фундамента: короткая последовательная волна (bootstrap → схема БД → контракты) и сразу за ней широкая параллельная (6–8 независимых линий). Чем раньше закрыты контракты, тем шире параллель.

### B3. Проектирование изоляции — главная работа при составлении плана

Изоляция не возникает сама; её проектируют ДО нарезки задач:

1. **Каркас репозитория** с явным владением директориями — первым разделом плана. Задачам раздаются директории, не файлы.
2. **Контрактные точки** (схема БД, типы контента, state пайплайна, codegen) — отдельные РАННИЕ задачи. Именно они разблокируют параллель; они же — кандидаты high-stakes.
3. **Stub-паттерн** для общего wiring: каркас (граф, роутинг) создаётся один раз со всеми заглушками; последующие задачи наполняют каждая свой файл и меняют одну строку подключения. Две задачи, меняющие wiring, — никогда параллельно.
4. **Append-only зоны**: миграции (только новые ревизии, перед интеграцией проверить единственность head). Общий devlog пишет только координатор; включение роутеров сериализуется.
5. **Сквозные задачи** (a11y-фиксы по всем областям, глобальные рефакторинги) — помечай «только соло», не ставь в волну с кем-либо.
6. Параллельные исполнители — в отдельных worktrees от проверенной интеграционной базы; интеграция и проверки после каждой задачи. Без изоляции — последовательно.

### B4. Приёмка: писать от лица reviewer'а

Reviewer не видел разговора и не верит исполнителю. Приёмка обязана быть проверяемой без автора:

- **Хорошо:** воспроизводимый сценарий («ученик с 60% не проходит дальше, с 80% — проходит»); метрика из спайка, которую надо перегнать («строгая точность ≥95%, галлюцинированные ID = 0»); негативный тест («redirect на приватный IP заблокирован»); инвариант («повторный запуск не перезаписывает готовые модули»).
- **Плохо:** «работает корректно», «код чистый», «покрыто тестами» (без «чем именно»).

Числа для приёмок берутся из артефактов спайков — ещё одна причина делать ресерч до плана.

### B5. Обвязка плана (обязательные разделы документа)

1. **Протокол агента** — прочитать контекст → проверить зависимости → своя область → применимые проверки обязательны → коммит-конвенция → отчёт координатору (только он ставит чекбокс после независимого ACCEPT и пишет devlog) → запрет scope creep.
2. **Каркас и владение** + правила общих точек (см. B3).
3. **Статус** — чекбоксы всех задач; единственный писатель — оркестратор, только после ACCEPT.
4. **«Обнаруженное»** — append-only секция для находок мимо scope.
5. **Раскладка по доступным слотам** — таблица «волна × роль»; по умолчанию максимум 3 активных дочерних агента, включая дизайн и review. Число независимых линий не равно числу одновременно запущенных агентов.
6. **Открытые вводные владельца** — таблица «что · что блокирует · где встроится»; ничего из этого не должно блокировать первую волну.

### B6. Маршрутизация — сразу при нарезке

Помечай кандидатов, пока контекст горячий (потом перенесёшь в `_generate.py` за минуту):
- **DESIGN** (deep-reasoner проектирует до реализации): L-размер, security, конкурентность, core-механика, версии данных.
- **HIGH_STAKES** (подмножество: адверсариальный дизайн): общие контракты/схемы, auth, изоляция данных, core wiring — то, что дорого переделывать.
- Всё остальное — стандарт (fast-worker → reviewer; scout только при необходимости). Задача «звучит важно» ≠ задача сложная.

## C. Формат плана под `tasks/_generate.py` (строгая грамматика)

Генератор проверяет структуру до записи. Запусти `--check` и сверь итоговое число задач с планом; не используй произвольные таблицы внутри волн.

```markdown
## <n>. Этап <N> — <Название>            ← n — номер секции документа, N — номер этапа
**Gate:** <исполняемый критерий>          ← допустимо **Gate (пояснение):** …; двоеточий внутри скобок быть не должно
### Волна <N.X> — <режим>                 ← например «параллельно (6 линий)», «последовательно»
| ID | Задача | Размер | Зависит | Владение | Контекст | Сделать / Приёмка |
|---|---|---|---|---|---|---|
| T0.1 | … | L | — | `пути/` | файлы | что сделать **Приёмка:** критерии |
```

Жёсткие требования:
- ID строго `T<этап>.<номер>` — иначе строка задачи отклоняется;
- ровно **7 колонок**; внутри ячеек нельзя символ `|` и переносы строк;
- маркер `**Приёмка:**` в последней колонке обязателен — по нему карточка делится на «Сделать» и «Приёмка»;
- задачи должны находиться внутри волн; текстовые пояснения допустимы, другие таблицы размещай до этапов;
- `RUNS` можно оставить пустым для имён `run-<этап>`; при явном заполнении в нём должны быть все этапы;
- повтор неизменного плана сохраняет файлы и статусы; изменение плана требует явного согласования/архивации, см. RUNTIMES.md.

## D. Чеклист качества бэклога (перед первым раном)

- [ ] Любая карточка `T*.md` понятна человеку, не видевшему проекта (тест самодостаточности — открой и прочитай глазами сабагента);
- [ ] внутри каждой волны области владения не пересекаются (проверь греп-проходом по колонке «Владение»);
- [ ] каждая приёмка проверяема reviewer'ом без разговора с исполнителем;
- [ ] контракты/схемы стоят в первой волне и помечены high-stakes;
- [ ] в плане нет решений, не подтверждённых ресерчем, — либо у решения есть артефакт, либо в карточке явно написано «мини-спайк внутри задачи»;
- [ ] хвосты ресерча замаплены на конкретные задачи;
- [ ] вводные владельца — в отдельной секции, первая волна от них не зависит;
- [ ] `python3 tasks/_generate.py` отработал, число задач в ранах совпало с планом;
- [ ] первый ран начинается с одной задачи (smoke), не с волны.

## E. Анти-паттерны (из обкатки)

- **«Сделать модуль X»** без владения и приёмки → два агента в одном файле и ACCEPT на честном слове.
- **Приёмка-пожелание** («должно работать») → reviewer штампует, брак едет дальше.
- **«Выберем библиотеку по ходу»** → выбор посреди рана: сабагент либо спросит (простой), либо решит сам (лотерея). Выбор — в research-фазу.
- **Карточка пересказывает спеку** вместо ссылки → при обновлении спеки карточка молча врёт. Ссылка + правило «при расхождении карточка проигрывает плану».
- **Задача-XL** («редактор целиком») → дробить по слоям: ядро / панель источников / интеграция перегенерации.
- **Статусы в разговоре**, а не в файлах → обрыв сессии теряет прогресс; состояние — в README, progress/result/review артефактах и devlog.
- **Ресерч без чисел** («выглядит достижимо») → метрика-обещание доезжает до прода непроверенной. Спайк обязан вернуть измерение.

## Актуальный runtime

Общий протокол — `assets/tasks/ORCHESTRATION.md` (после установки: `tasks/ORCHESTRATION.md`). Он уточняет историческую методику: scout по необходимости, единственный писатель devlog/статусов, отдельный gate, ограниченный ремонт. Формат владения — literal относительные пути через запятую, без glob; зависимости — ID через запятую. Неизвестные зависимости, циклы, поздние зависимости и пересечения владения параллельной волны отклоняются генератором.
