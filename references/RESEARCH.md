# Исследование и решения

Дата проверки источников: 2026-09-12. Это анализ устройства и документации,
не измерение эффективности на реальных запусках. Ссылки на upstream main
изменяемые; приведённые выводы относятся к прочитанной версии.

## Что уже было сильным

Четыре специализированные роли, самодостаточные брифы, владение файлами,
предварительный дизайн рискованных задач, независимый reviewer, этапные gate
и файловый прогресс — полезная основа для больших задач. Методика бэклога
связывает исследование неизвестных с проверяемыми критериями разработки.

## Обнаруженные слабые места

| Наблюдение в исходниках | Последствие | Принятое решение |
|---|---|---|
| Только `.claude`, CLAUDE.md и команда Claude; Fable как обязательный тимлид | Нельзя непосредственно использовать в Codex | Общий протокол + адаптеры, доступность моделей проверяется |
| `_generate.py` перезаписывает README | Потеря прогресса даже между ранами | Повтор неизменного плана — no-op, изменение — явное согласование |
| Парсер пропускает нераспознанные строки; нет проверки графа | Неполный бэклог, циклы, несуществующие зависимости | Проверка структуры, ID, графа, порядка до записи |
| Владение проверяется только инструкциями | Два исполнителя меняют общий путь | Проверка literal-prefix конфликтов; семантические конфликты вручную |
| Все исполнители пишут общий devlog | Конфликт даже при независимом коде | Единственный писатель — координатор |
| Worktrees описаны в BACKLOG, но не в runtime-команде | Различные практики изоляции | Единое правило: параллельные writers только в отдельных worktrees |
| Лимит ≤3 задач, но внутри каждой несколько агентов | Превышение лимита активных агентов | Считать всех детей, запрет рекурсивного dispatch |
| Scout обязателен для любой карточки | Лишний вызов на уже известном контексте | Scout по неопределённости/объёму |
| Продолжение определяется чекбоксами/devlog | Повтор живого worker, потеря числа попыток | Артефакты progress/result/review и сверка с рабочим деревом |
| Первый незакрытый ран определяется только задачами | Пропуск непройденного gate | Отдельные gate checkbox и evidence |
| Жёсткие 10–20 задач и фиксированная экономика моделей | Не соответствует сложности и доступности хоста | Границы по интеграции, маршрутизация по риску |
| Знания остаются в журнале | Следующий ран повторяет исследование | Индексируемые проверенные решения в docs/solutions |

## Что взято из Every

[Compound Engineering](https://github.com/EveryInc/compound-engineering-plugin)
связывает планирование, исполнение, упрощение, review и сохранение знаний.
Для этого проекта полезнее сам цикл обратной связи, чем импорт большого
каталога специалистов или обязательное прохождение всех команд.

[ce-work](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-work/SKILL.md)
разделяет самостоятельное выполнение и возврат результата внешнему
оркестратору. Здесь workers возвращают проверяемый отчёт; приёмку, интеграцию
и разрешение дальнейших действий сохраняет координатор.

[ce-compound](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-compound/SKILL.md)
сохраняет знания о проверенно решённых нетривиальных проблемах. Взяты критерий
полезности урока и последующее чтение подходящих решений, без копирования
upstream-кода и без обязательной заметки после каждой задачи.

[ce-plan](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-plan/SKILL.md)
отделяет планирование от реализации и допускает масштабирование плана по
задаче. Здесь размер рана определяется gate и проверяемостью результата,
а не фиксированным количеством карточек.

## Совместимость и дополнительные подходы

[Codex skills](https://learn.chatgpt.com/docs/build-skills): единый SKILL.md
с дополнительными ресурсами подходит для локальной установки. Для discovery
используются `.agents/skills` проекта и пользователя; вызов в Codex — `$имя`.

[Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents):
нативные роли описываются TOML в `.codex/agents`. Мы генерируем только имя,
описание и инструкции, оставляя выбор модели среде; fallback — передать тело
роли доступному сабагенту. Нет предположения о едином наборе инструментов всех
клиентов. Изоляция прав наследуется от среды и не подменяется ролью в prompt.

[Claude subagents](https://code.claude.com/docs/en/sub-agents): Markdown-роли
поддерживают model/effort и worktree isolation. Нельзя считать worktree
автоматически ответвлённым от нужного интеграционного HEAD: протокол требует
проверять базу. Bash не делает роль технически read-only.

[Claude skills](https://code.claude.com/docs/en/skills): setup остаётся
совместимым со структурой `.claude/skills`; команда запуска остаётся нативной.

## Что сознательно отложено

- Автоматическая интеграция и строгая машина состояний с блокировками: текущий
  проект — инструкции, не scheduler. Текстовый протокол не гарантирует соблюдение
  агентом; серверный контроль переходов потребовал бы отдельной реализации.
- Автоматический merge изменённых планов со статусами: перенос ACCEPT на новые
  критерии опаснее явного отказа и ручной сверки.
- Загрузка множества review-агентов на каждую задачу: повышает цену и время,
  полезность надо измерять. Независимый reviewer остаётся обязательным.
- Автоматическая смена моделей/прав и автопубликация: не нужны для переносимости.
- Обязательный research каждого решения: спайки нужны там, где неизвестное
  действительно блокирует архитектуру или обещанную метрику.

## Как измерять улучшение

На одном репозитории подобрать сравнимые наборы задач: простая реализация,
изменение контракта, задача с миграцией, независимая пара задач. Зафиксировать
версии хостов, фактические модели, критерии и лимит. Сравнить старую и новую
настройки по времени до интегрированного ACCEPT, first-pass acceptance,
числу возвратов, потерям состояния, конфликтам и расходу токенов (если доступен).
Отдельно прервать сессию после реализации до review и после review до gate:
продолжение должно сохранить попытки и не повторить живого исполнителя.

Автотесты этого репозитория проверяют установку, парсинг, повторную генерацию
и сохранность файлов. Они не подтверждают экономию, качество реальных моделей,
обнаружение скиллов конкретным клиентом или соблюдение протокола агентами.
