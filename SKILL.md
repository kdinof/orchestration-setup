# Orchestration Setup

Собери в текущем проекте инфраструктуру оркестрации: главная сессия (Fable 5) — оркестратор-тимлид, реализацию делают сабагенты на дешёвых моделях, задачи выполняются «ранами» по 10–20 штук с приёмкой каждой.

Ассеты в `assets/` этого скилла — **рабочие, обкатанные файлы** (проект AI Course Builder, 55 задач). Копируй их как есть; не переписывай и не «улучшай» — каждая строчка в них закрывает конкретные грабли (наследование effort, самодостаточность брифов, недоверчивая приёмка). Адаптируй только места, помеченные ниже.

`SKILL_DIR` ниже = базовая директория этого скилла (указана при его загрузке).

## Что получится

```
.claude/agents/        scout, fast-worker, deep-reasoner, reviewer (модели закреплены)
.claude/commands/      /orchestrate — запуск/продолжение рана
tasks/_generate.py     нарезает план на раны; tasks/run-*/ — карточки и статусы
docs/devlog.md         append-only журнал агентов
CLAUDE.md              + секция Orchestration workflow (роли, правила, протокол рана)
```

## Шаг 1 — инвентаризация (перед копированием)

Проверь, что уже есть в проекте: `CLAUDE.md`, `.claude/agents/`, `.claude/commands/`, план задач, `docs/devlog.md`. Ничего не затирай молча:

- `CLAUDE.md` существует → **дописывай** секцию оркестрации в конец, не заменяй файл.
- Агент/команда с таким же именем уже есть → покажи пользователю дифф и спроси.
- План задач ищи по признакам: markdown с таблицей задач (ID, зависимости, приёмка) в `docs/`, `outputs/`, `plan*`, `PLAN*`, `tasks*`.

## Шаг 2 — скопировать ассеты

```bash
mkdir -p .claude tasks docs
cp -R "$SKILL_DIR/assets/agents"   .claude/agents
cp -R "$SKILL_DIR/assets/commands" .claude/commands
cp    "$SKILL_DIR/assets/tasks/_generate.py" tasks/
[ -f docs/devlog.md ] || printf '# Devlog — append-only журнал агентов\n\n---\n' > docs/devlog.md
cat "$SKILL_DIR/assets/CLAUDE-orchestration.md" >> CLAUDE.md
```

(При существующих файлах — по правилам шага 1 вместо слепого `cp`.)

## Шаг 3 — план задач (единственное настоящее предусловие)

Оркестрации нужен план, где у каждой задачи есть: **ID · размер S/M/L · зависимости · владение файлами · контекст-файлы · проверяемая приёмка**, задачи сгруппированы в волны, этапы закрыты gate'ами. Точная грамматика — в докстринге `tasks/_generate.py`. Качество плана = качество прогона: владение файлами защищает параллельных агентов от конфликтов, приёмка даёт reviewer'у критерии.

- **План есть** → сверь с грамматикой; при расхождениях предложи пользователю привести к формату (обычно это переименование заголовков и колонок, не переписывание содержимого).
- **Плана нет** → спроси пользователя, какой путь:
  - *Быстрый* (есть PRD/описание, решения в основном приняты): составь план вместе с ним — задачи-единицы работы одного агента за сессию (S ≤1ч, M 1–3ч, L 3–6ч), изолированные области файлов, волны с непересекающимся владением, gate-критерии этапов. Размеры и gate'ы подтверждай у пользователя — это его решения.
  - *Полный* (новый продукт, непроверенные допущения): прочитай `references/BACKLOG.md` — методика с research-фазой до плана (неизвестные закрываются волнами агентов ДО того, как лягут в план; «наверное» в плане = переделка контракта посреди рана).

## Шаг 4 — настроить под проект

1. **CLAUDE.md, блок Sources of truth** — заполни реальными путями (PRD, план, спеки) и командами линтеров/тестов проекта. Возьми факты из репозитория, не выдумывай; чего нет — спроси.
2. **`tasks/_generate.py`, блок «НАСТРОЙКА ПОД ПРОЕКТ»** — `PLAN`, `RUNS` (этап → папка рана), `ALWAYS_CONTEXT`, и два списка маршрутизации, которые ты классифицируешь сам по критериям:
   - `DESIGN` (deep-reasoner проектирует до реализации): L-размер, security, общие контракты/схемы, конкурентность, core-механика.
   - `HIGH_STAKES` (подмножество DESIGN, дизайн адверсариально deep-reasoner ∥ reviewer): общие контракты, auth, изоляция данных, core wiring — то, что дорого переделывать.
   
   Покажи пользователю получившуюся классификацию (задача → маршрут → почему) и дождись подтверждения — это суждение о рисках, оно за владельцем.
3. **`.claude/agents/*.md`** — обычно без правок; максимум 1–2 строки контекста стека в тела fast-worker/reviewer.

## Шаг 5 — нарезать и проверить

```bash
python3 tasks/_generate.py
```

Проверь: число задач в выводе = числу в плане; в каждом ране 10–20 задач (сильно больше — предложи пользователю разбить этап в плане); открой одну карточку `T*.md` и убедись, что она самодостаточна как бриф (владение, контекст, приёмка, маршрут на месте).

Перегенерация затирает чекбоксы статуса — предупреди пользователя запускать генератор только между ранами.

## Шаг 6 — отчёт и запуск

Сообщи пользователю, что создано, и как запускать:

```
claude              # в корне проекта
/model              # Fable 5, Reasoning effort: High
/orchestrate run-0-<имя>     # или без аргумента — первый незакрытый ран
```

Команда сама отличает старт рана (раскладка + подтверждение) от продолжения после обрыва. Посоветуй smoke-тест: первый ран начать с одной задачи, посмотреть качество брифа, дизайн-файла `T*-design.md` и вердикта reviewer — потом отпускать волнами.

## Инварианты (это причины, по которым система работает — не ослабляй их при адаптации)

1. **Оркестратор не кодит** — начал кодить, план деградирует, контекст засоряется.
2. **Бриф самодостаточен** — сабагент не видит разговора; всё нужное в карточке и брифе.
3. **Состояние в файлах** (README рана, devlog, `T*-design.md`) — сессию можно убить и продолжить.
4. **Приёмка недоверчива** — reviewer с чистым контекстом сам гоняет тесты; чекбокс только после ACCEPT.
5. **Параллель ≤3** и только непересекающееся владение; общие контракты — последовательно.
6. **Модели не меняются ролями** — Haiku не решает, Sonnet не проектирует, Opus не печатает боилерплейт.
