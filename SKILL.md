# Orchestration setup

Разверни инфраструктуру в выбранном проекте. Установка не означает запуск
разработки. `SKILL_DIR` — директория этого файла; все скрипты и ассеты лежат
внутри неё. Пользовательские инструкции имеют приоритет над шаблонами.

## 1. Инвентаризация

Проверь инструкции проекта, текущие изменения, `CLAUDE.md`, `AGENTS.md`,
`.claude/`, `.codex/`, `.agents/skills/`, `tasks/`, план и команды проверки.
Выбери `claude`, `codex` или `both` по запросу. Если хост не назван, используй
текущий. Для деталей адаптации прочитай [RUNTIMES.md](references/RUNTIMES.md).
Не считай доступность сабагентов или конкретных моделей гарантированной.

## 2. Установка инфраструктуры

Используй установщик вместо ручного копирования. Сначала посмотри результат:

```bash
python3 "$SKILL_DIR/scripts/install.py" setup --target both --project /path/to/project --dry-run
python3 "$SKILL_DIR/scripts/install.py" setup --target both --project /path/to/project
```

Замени target и путь. Скрипт добавляет ограниченные маркерами секции инструкций,
сохраняет локальную конфигурацию и devlog; одинаковый повторный запуск ничего
не меняет. При отличающихся файлах показывает diff и отказывается от записи.
Сначала подготовь конкретное согласование конфликта: сохрани локальные правила,
примени уже разрешённые изменения; спрашивай только когда действительно нужно
выбрать между несовместимыми пользовательскими настройками. Не удаляй файлы
ради обхода проверки конфликта. Старые немаркированные секции требуют ручной
миграции; инструкция — в RUNTIMES.md.

Для Claude установщик также ставит хук `.claude/hooks/orch_guard.py` и аддитивно
дописывает его в `.claude/settings.json` (остальные настройки не трогаются;
отказаться — `--no-claude-hooks`). Хук закрепляет кодом два правила: координатор
не правит код во время рана, чекбокс — только после записанного ACCEPT reviewer;
и собирает метрики агентов. Он же экономит время на тестах: заполни в
`tasks/checks.json` точную команду полного набора (`full`) — fast-worker её не
запустит (только scoped), а повтор уже прошедшего прогона на неизменном коде
хук отклонит и отдаст сохранённый результат. Отчёт показывает долю времени на
проверки — по нему решай, нужен ли полный набор на каждую задачу. Проектные хуки работают после принятия доверия к
папке — скажи об этом пользователю.

## 3. Настройка под проект

Заполни `tasks/PROJECT.md` фактами: требования, план, спецификации, реальные
команды проверки, runtime, доступные модели, лимит агентов и изоляцию.
Не перезаписывай настройки разрешений или глобальную конфигурацию хоста.
Claude получает роли с модельными алиасами; Codex — TOML-роли с наследованием
модели сессии. Если пользователь задал модели, проверь доступность и укажи
поддерживаемые model/effort в соответствующих файлах. Отрази фактический маршрут. Для больших ранов предложи профиль
`--codex-profile balanced` (Luna → scout, Terra → worker, Astra → design/review),
если модели доступны и пользователь хочет распределить нагрузку. Своя таблица:
`--codex-models /path/to/models.json`, формат в RUNTIMES.md. Без выбора профиля
сохраняется inherit. Проверь реальное применение роли/модели при первом dispatch;
установка файлов не доказывает, что клиент применил настройки.

В `tasks/_generate.py` настрой `PLAN`, при необходимости `RUNS`, `DESIGN`,
`HIGH_STAKES`, `ALWAYS_CONTEXT`. L автоматически требует design; auth, общие
контракты, изоляция данных и сложная конкурентность — кандидаты HIGH_STAKES.
Покажи классификацию с причинами; обычные технические решения принимай в рамках
запроса, продуктовые развилки и недостающие критичные вводные уточняй.

## 4. План и генерация

При отсутствии плана составь его из требований. Для значительных неизвестных
прочитай [BACKLOG.md](references/BACKLOG.md), проведи ограниченные спайки.
Не запускай многодневный research для уже решённых вопросов. Грамматика таблиц
описана в докстринге генератора; пример — [example-plan.md](references/example-plan.md).
Проверь самодостаточность брифов, измеримую приёмку, владение, зависимости, gate.

```bash
python3 tasks/_generate.py --check
python3 tasks/_generate.py
```

Генератор проверяет план до записи, отсекает неизвестные/циклические зависимости
и пересечение путей в параллельных волнах. Семантические конфликты (общая БД,
порты, codegen, lockfile) проверяй отдельно. Повторный запуск неизменного плана
сохраняет прогресс. Изменившийся план или старые раны без manifest требуют
явного согласования/архивации, не слепой перегенерации.

## 5. Проверка и отчёт

Открой карточку и README, проверь ссылки, фактический маршрут и команды.
Сообщи созданные файлы и ограничения. Для Claude напомни: прогресс и решения —
README рана (Rulings сверху по цене ошибки), метрики —
`python3 .claude/hooks/orch_guard.py report`. Claude: `/orchestrate run-0`;
Codex: `$orchestrate run-0`. После первой установки перезапусти хост, если
новые роли/скиллы не видны. Smoke первой задачи выполняй, только если запрос
включает выполнение задач. Проверки установщика не доказывают качество агентов.

Общий протокол в `tasks/ORCHESTRATION.md`: самодостаточные брифы, единый писатель
статуса, изоляция исполнителей, независимая приёмка, лимит попыток, отдельный
интеграционный gate и сохранение проверенных уроков. Обоснование изменений и
план оценки — [RESEARCH.md](references/RESEARCH.md).
